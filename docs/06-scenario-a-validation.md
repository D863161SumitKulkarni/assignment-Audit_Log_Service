# Scenario A Validation

## Scope

Scenario A validates the core tamper-evident audit flow:

- Append audit events through the API.
- Query events using the required filters.
- Confirm server-assigned timestamps and linked hashes.
- Verify a valid chain.
- Tamper with a stored payload directly in PostgreSQL.
- Verify that the tampering is detected and reported.

The examples use Windows PowerShell with `curl.exe`. Replace placeholder values with local values where necessary.

## 1. Start the Application

Open PowerShell in `backend/audit-log-service` and provide the local PostgreSQL password through the environment instead of committing it to configuration:

```powershell
$env:DB_PASSWORD = "<local-postgres-password>"
$env:AUDIT_ADMIN_PASSWORD = "<local-admin-password>"
$env:AUDIT_AUDITOR_PASSWORD = "<local-auditor-password>"
.\mvnw.cmd spring-boot:run
```

The default local usernames are `admin` and `auditor` unless overridden by environment variables. The application should start on port `8080`.

Confirm Swagger is available:

```powershell
curl.exe -i http://localhost:8080/swagger-ui/index.html
```

Expected result: `HTTP/1.1 200`.

For the examples below, set shell variables matching the running application:

```powershell
$adminUser = "admin"
$adminPassword = "<local-admin-password>"
$auditorUser = "auditor"
$auditorPassword = "<local-auditor-password>"
```

If the local placeholder passwords are still active, use `change-me-admin` and `change-me-auditor`.

## 2. Create the First Audit Event

Only an `ADMIN` can append an event.

```powershell
curl.exe -i -u "$adminUser`:$adminPassword" `
  -H "Content-Type: application/json" `
  -d '{"eventType":"ACCOUNT_VIEWED","actorId":"scenario-a-user","resourceType":"CLIENT_ACCOUNT","resourceId":"scenario-a-account","payload":{"screen":"account-summary","source":"scenario-a"}}' `
  http://localhost:8080/api/audit/events
```

Expected result: `HTTP/1.1 201 Created`.

Expected response characteristics:

- `eventId` is generated by the server.
- `eventTimestamp` is generated by the server.
- `previousHash` is 64 zero characters because this is the first event.
- `currentHash` is a 64-character lowercase SHA-256 value.
- `archived` and `redacted` are `false`.

Save the returned `eventId` for later checks.

## 3. Create the Second Audit Event

```powershell
curl.exe -i -u "$adminUser`:$adminPassword" `
  -H "Content-Type: application/json" `
  -d '{"eventType":"ACCOUNT_EXPORTED","actorId":"scenario-a-user","resourceType":"CLIENT_ACCOUNT","resourceId":"scenario-a-account","payload":{"format":"json","source":"scenario-a"}}' `
  http://localhost:8080/api/audit/events
```

Expected result: `HTTP/1.1 201 Created`.

Confirm that the second event's `previousHash` equals the first event's `currentHash`. This demonstrates the chain link.

## 4. Query Events by `actorId`

```powershell
curl.exe -i -u "$auditorUser`:$auditorPassword" `
  "http://localhost:8080/api/audit/events?actorId=scenario-a-user&page=0&size=20"
```

Expected result: `HTTP/1.1 200 OK` with both Scenario A events in `content`.

## 5. Query by `resourceType` and `resourceId`

The query supports both filters together:

```powershell
curl.exe -i -u "$auditorUser`:$auditorPassword" `
  "http://localhost:8080/api/audit/events?resourceType=CLIENT_ACCOUNT&resourceId=scenario-a-account&page=0&size=20"
```

Expected result: `HTTP/1.1 200 OK` with the matching client-account events.

## 6. Query by `eventType`

```powershell
curl.exe -i -u "$auditorUser`:$auditorPassword" `
  "http://localhost:8080/api/audit/events?eventType=ACCOUNT_VIEWED&page=0&size=20"
```

Expected result: `HTTP/1.1 200 OK` containing only events with `eventType=ACCOUNT_VIEWED`.

## 7. Query by Time Range

Use the timestamp returned by the first and second append responses. The values below are examples only:

```powershell
$from = "2026-08-19T00:00:00Z"
$to = "2026-08-19T23:59:59Z"

curl.exe -i -u "$auditorUser`:$auditorPassword" `
  "http://localhost:8080/api/audit/events?from=$from&to=$to&page=0&size=20"
```

Expected result: `HTTP/1.1 200 OK` with events whose `eventTimestamp` is within the inclusive range.

A malformed timestamp should be rejected:

```powershell
curl.exe -i -u "$auditorUser`:$auditorPassword" `
  "http://localhost:8080/api/audit/events?from=not-an-instant"
```

Expected result: `HTTP/1.1 400 Bad Request`.

## 8. Verify the Chain

```powershell
curl.exe -i -u "$auditorUser`:$auditorPassword" `
  http://localhost:8080/api/audit/verify
```

Expected result for a valid chain: `HTTP/1.1 200 OK` with a response similar to:

```json
{
  "chainIntact": true,
  "checkedRecords": 2,
  "firstBrokenEventId": null,
  "firstBrokenDatabaseId": null,
  "violationType": null,
  "expectedValue": null,
  "actualValue": null,
  "message": "Audit event hash chain is intact"
}
```

A broken chain is still a valid verification response and returns HTTP 200. The `chainIntact` value communicates the integrity result.

## 9. Tamper Directly in PostgreSQL

The repository includes [database/tamper-test.sql](../database/tamper-test.sql). The prompt referred to `tamper-test.sq1`; the actual file uses the correct `.sql` extension.

The script:

1. Displays the first few records.
2. Adds `_tamper_test` to `payload_original` on the first record.
3. Leaves `current_hash` unchanged.
4. Commits the modification so the running API can observe it.
5. Displays the modified record.

Run it from a PowerShell prompt with `psql` available:

```powershell
$env:PGPASSWORD = "<local-postgres-password>"
psql -h localhost -U postgres -d auditlogdb -f ..\..\database\tamper-test.sql
Remove-Item Env:PGPASSWORD
```

Alternatively, open `database/tamper-test.sql` in pgAdmin or another PostgreSQL client and execute it against `auditlogdb`.

**Warning:** Run this only against a local test database. It intentionally changes an audit record without updating its hash.

## 10. Verify Again After Tampering

```powershell
curl.exe -i -u "$auditorUser`:$auditorPassword" `
  http://localhost:8080/api/audit/verify
```

Expected result: `HTTP/1.1 200 OK` with:

```json
{
  "chainIntact": false,
  "checkedRecords": 1,
  "firstBrokenEventId": "<tampered-event-id>",
  "firstBrokenDatabaseId": 1,
  "violationType": "CURRENT_HASH_MISMATCH",
  "expectedValue": "<recalculated-hash>",
  "actualValue": "<stored-hash>",
  "message": "Current hash does not match the recalculated event hash"
}
```

The exact `checkedRecords` and database ID depend on the local database contents. The important assertions are:

- HTTP status is `200`.
- `chainIntact` is `false`.
- The first inconsistent event is identified.
- `violationType` is `CURRENT_HASH_MISMATCH`.

## 11. Expected Violation Type

Because the tamper script changes `payload_original` but does not update `current_hash`, the expected violation is:

```text
CURRENT_HASH_MISMATCH
```

A `PREVIOUS_HASH_MISMATCH` indicates that a record's link to the genesis hash or preceding record is wrong instead.

## 13. Troubleshooting Notes

### Swagger or API connection refused

Confirm the application is running on port 8080:

```powershell
Test-NetConnection localhost -Port 8080
```

Start it from `backend/audit-log-service` with the required environment variables.

### HTTP 401 Unauthorized

The endpoint is protected. Use valid `admin` or `auditor` credentials with `curl.exe -u`.

### HTTP 403 Forbidden

The authenticated user does not have the required role. Appending, redaction, and retention require `ADMIN`; read-only queries and verification accept `AUDITOR`.

### HTTP 400 for a valid-looking request

Check the JSON body, UUID path value, ISO-8601 timestamps, page number, and page size. Page size must be between 1 and 100.

### HTTP 500 with `audit.event` missing

Confirm PostgreSQL is running, `auditlogdb` exists, `DB_PASSWORD` is set, and the application has been restarted after configuration changes. Local Hibernate namespace creation is enabled for the prototype.

### Chain verification reports a mismatch immediately

Inspect the first record and the application logs. A previously tampered local row should remain inconsistent by design. Do not silently update hashes to hide the result; restore a local test database from a clean backup or recreate the test database for a fresh Scenario A run.

### PostgreSQL tamper script cannot connect

Check that `psql` is installed, `PGPASSWORD` is set for the command, the database is `auditlogdb`, and the user is `postgres`.

### Empty query result

Confirm the append requests returned HTTP 201, use the exact actor/resource values, and do not accidentally query a different database or application profile.
